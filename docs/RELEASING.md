# Releasing

## Cutting a release

```powershell
.\bump_version_and_release.ps1 -DryRun    # preview the notes, change nothing
.\bump_version_and_release.ps1            # feature bump: 0.46.9 -> 0.47.0
.\bump_version_and_release.ps1 -Patch     # patch bump:   0.46.9 -> 0.46.10
.\bump_version_and_release.ps1 -Polish    # + translation and a highlights paragraph
```

The script reads the version from `flutter_client/pubspec.yaml`, bumps it,
commits, tags, pushes, and creates the GitHub release. Per the project
convention, a release is a **feature** bump unless you pass `-Patch`.

`-DryRun` prints the notes and stops. It runs before the clean-tree check, so
you can preview mid-work.

## Release order

Deploy the server right after tagging. The tag publishes the Android APK on the
GitHub release at once, while the server deploy is a separate manual step. In
the gap, a new app build talks to the old server and falls back to the
whole-map day-notes save, which is only safe on a server that predates the
per-day endpoint. Keep the gap short.

## Raising the minimum client version

The server reports `min_client_version` on `GET /api/version`, from the
`MIN_CLIENT_VERSION` environment variable (default `0.0.0`, which blocks
nobody). A build below it is stopped: the Android app shows an "Update
required" screen with a link to the latest GitHub release, and the web app
shows a reload bar that cannot be dismissed.

- **When.** Only when an older build would do harm against the new server, for
  example by saving data the server now rejects. Not for ordinary releases:
  builds lag the server routinely.
- **How.** Set `MIN_CLIENT_VERSION` (plain `x.y.z`, no `v`) in the server's
  runtime environment and redeploy. Raise it only after the release that
  carries the fix is published, so the update link leads somewhere. Setting it
  back to `0.0.0` lifts the block on the next check (app start or resume).
- **Pre-gate builds are never prompted.** A build installed before this gate
  existed does not know to check, so the release page is the only notice its
  user gets. A change that breaks installed APKs therefore needs an
  `Upgrade-Note:` trailer on its commit, telling Android users to install the
  new APK first.

## Writing a release note

Release notes are generated by [`scripts/release_notes.py`](../scripts/release_notes.py)
from the commits in the range. It groups by type, maps the commit scope to a
user-facing area, splits app changes from server ones, links issue refs, and
collapses internal churn.

What it **cannot** do is turn a commit subject into a user benefit. No parser
gets from

> `fix(strava): enforce the API quota process-wide, not per request`

to *"Strava import no longer risks exceeding Strava's request quota."* — that
information isn't in the commit. So write it yourself, at commit time, in a
`Release-Note:` trailer:

```
fix(strava): enforce the API quota process-wide, not per request (#130)

<the usual body, for whoever reads the diff>

Release-Note: Strava import no longer risks exceeding Strava's request
quota, which could temporarily cut off sync.
```

The trailer wins over the subject line in the release notes. **Only user-visible
changes need one** — typically three or four per release. Everything else falls
back to the cleaned-up subject, which is fine for a fix whose subject already
reads plainly.

Two supported trailers:

| Trailer | Effect |
|---|---|
| `Release-Note:` | Replaces the subject in the notes. Write it for someone who uses the app. |
| `Upgrade-Note:` | Adds a line under **⚠️ Upgrade notes** — config that must change, a manual step, anything that breaks on upgrade. A `feat!:`/`fix!:` breaking marker implies one. |

Both may wrap across lines; a blank line ends them, and so does an attribution
trailer stacked right under them (`Co-Authored-By:`, `Signed-off-by:`,
`Claude-Session:`).

Write subjects and trailers as plain text. The generator escapes `<`, `>` and `&`
outside backtick code spans, because GitHub strips anything that looks like an
HTML tag: an unescaped `User=<deploy-user>` rendered as `User=`. That also
means markup can't be smuggled in: `<br>` shows as `<br>`. Backticks still make
code spans, and their contents are shown as typed.

### Write them in English

**Release notes are published in English**, so `Release-Note:` and
`Upgrade-Note:` trailers are written in English — whatever language the commit
subject, the body, or the conversation that produced it was in.

"Write it for someone who uses the app" is about *vocabulary*, not language: say
"Strava import no longer stalls", not "enforce the API quota process-wide". It
has never meant "write it in the reader's mother tongue" — the app has one
release page and it is in English.

This is worth stating because it has already gone wrong: v0.48.0 shipped with
sixty Portuguese bullets between the English ones, and had to be rewritten by
hand after the fact. Two things now catch it:

- `release_notes.py` flags entries that don't look like English and lists them
  on stderr — always, `-DryRun` included. Preview before you tag and you'll see
  them while the commits are still amendable.
- `-Polish` translates the flagged entries into English before rendering (see
  below). It never touches an entry that already reads as English.

The detection is deliberately blunt — it only has to spot a whole sentence in
another language. A bullet that names a Portuguese place or product is fine.

## What lands where

| Commit | Section |
|---|---|
| `feat: …` | 🚀 New |
| `fix: …`, `perf: …` | 🐛 Fixed |
| anything else (`chore`, `docs`, `test`, `refactor`, …) | collapsed under *Internal changes* |
| any scope in the internal set (`ci`, `release`, `deps`, `docker`, `deploy`, `test`) | collapsed, whatever its type |
| merge commits, `chore: bump version` | dropped entirely |

Within **New** and **Fixed**, changes split into *In the app* and *Server &
deployment* — one tag ships both the Flutter client and the FastAPI server, and
the two have different readers. The sub-headings only appear when a section
actually contains both.

Audience and area come from the commit scope (see `AREAS` in
`scripts/release_notes.py`), falling back to the paths the commit touched —
anything under `flutter_client/` is app-visible. **Add a scope to the table when
you introduce one**: an unmapped scope still lands in the right section, but is
labelled with the raw scope name rather than something a reader recognises.

## Previewing any range

```powershell
python scripts/release_notes.py --from v0.46.9 --to HEAD
python scripts/release_notes.py --from v0.46.0 --to v0.46.9 --version v0.46.9
```

Useful for checking how a commit will read *before* it's tagged — and for
seeing whether a change needs a `Release-Note:` trailer.

## Polish (`-Polish`)

`-Polish` is the one layer that calls out to Claude. It does two things:

1. **Translates** any entry the language check flagged into English, leaving
   entries that already read as English exactly as they were. Only the flagged
   lines are sent, and if the answer doesn't come back one-for-one the
   originals are kept and still warned about.
2. **Highlights** — a two-or-three sentence intro paragraph summarising the
   release, written from the (now English) notes.

It is entirely optional:

```powershell
pip install anthropic          # not in requirements.txt — release tooling only
$env:ANTHROPIC_API_KEY = "..."  # or: ant auth login
.\bump_version_and_release.ps1 -Polish
```

Missing package, missing key, network failure, or a refusal all degrade to the
same thing: a warning on stderr and the notes rendered without the paragraph.
A release is never blocked by it.

`anthropic` is deliberately kept out of `requirements.txt` — it would ship in
the server image for no reason.

## Privacy policy and terms of service

`legal/privacy.html` and `legal/terms.html` are served at `/privacy` and
`/terms` (issue #421). They ship in the image, so a release is what publishes a
change to them.

- **They must not ship with placeholders.** Facts the code cannot know are
  written as `{{NAME}}`, and
  `tests/test_legal_pages.py::test_legal_pages_have_no_unfilled_placeholders`
  fails while any remain. That failure is the gate: fill the values in, never
  skip the test.
- **They describe what the code does.** A change that collects something new,
  sends data to a new third party or changes how long something is kept needs
  the matching edit to `legal/privacy.html` in the same pull request.
- **Change the "Last updated" date** whenever the text changes, and give the
  commit a `Release-Note:` saying what changed. Both pages promise to tell users
  about significant changes before they apply, so an email or an in-app notice
  goes out ahead of such a release.
